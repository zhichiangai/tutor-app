# V5.4｜Team 超額付款、預收款與管理者確認抵扣（設計基準）

> **狀態：設計草案，尚未實作或驗收。** 此分支堆疊在 V5.3 PR #55，PR #55 未完成 Chromium 隔離 E2E 前不得宣告 V5.4 GO。
> 不合併 Main、不部署 Production、不執行正式 Supabase Migration。所有新帳務測試限隔離 Supabase 的合成學生／課程／付款。

## 一、已確認的產品規則

1. **超額款項：B**。管理者可將同 Team **同一位學生**多付的部分確認成預收款；日後可抵扣該學生其他已確認課程應收，或在另行實作的退款流程中處理。
2. **預收抵扣：C**。系統提出科目、課程和抵扣金額建議，**必須由現任 Team 管理者再次確認**才會入帳。建議永遠不是交易。
3. **部分付款／跨科目分配：B**。可按同 Team 同學生的數學、英文等科目及不同月份分配，也能多筆付款結清同一堂課。
4. **管理者確認：A**。確認後立即生效，任何更正須使用追加式稽核；不能直接 UPDATE 原始金額以抹去歷史。
5. 「已付款」僅代表**管理者人工核對並確認的款項**，不等於系統已證實銀行入帳或完成金流平台交易。
6. 家長自行回報、家長通知、退款、金流串接與會計更正皆需各自的權限與流程；不能假裝已實作。學生頁面不可出現學費。

## 二、必須沿用 V5.3 的資料邊界

- Team 的主鍵是 `public.v5_teams.id`，**不等於** V4 個人 workspace；使用 `anchor_workspace_id` 作既有治理與鎖定相容性。
- 學生使用 `public.v5_team_students.id`，不得把 V4 `students` 當成 V5 帳本歸屬。
- 課程應收沿用 `tutor_private.v5_team_lesson_fees` 的確認快照。
- 付款來源沿用 `tutor_private.v5_team_payment_reports`、付款明細與 `v5_team_payment_audit`；新的預收款**只能引用一筆既有、由管理者確認的付款**，不可憑空產生餘額。
- V4 `payment_batches`、`lesson_records`、舊家長收款及歷史課程**零寫入**。

## 三、建議增量資料模型（待 Migration 實作）

| 私有資料結構 | 職責 | 不變量 |
|---|---|---|
| `v5_team_advance_credits` | 某筆已確認付款所建立的原始預收款，記錄 Team、學生、付款 ID、金額與確認人 | 同一筆付款最多建立一筆、金額為正、不可直接改寫 |
| `v5_team_advance_applications` | 預收款抵扣至已確認應收課程的不可變分錄 | 僅同 Team 同學生、金額正數，不可超過可用餘額或課程未結清額 |
| `v5_team_advance_audit` | 建立預收款、確認抵扣及未來沖銷操作歷史 | 後端追加、附操作者與時間，不准前端直接讀寫 |

餘額一律由**原始預收款 − 已確認抵扣**推導，不以可任意覆寫的 `balance` 欄位作為帳務真相。退款尚未實作前不計入推導。

### 金額守恆

同一筆付款確認的瞬間：
```text
已確認人工付款 = 直接分配到應收的金額 + 新增預收款金額
```

預收款後續任一時刻：
```text
原始預收款 = 歷次已確認抵扣總額 + 尚可抵扣餘額
```

同一堂課：
```text
已確認應收 = 直接付款分配 + 預收款抵扣 + 尚未結清
```

所有值使用 **TWD integer cents**，不得使用浮點金額。三條等式都要由資料庫交易與 E2E 驗證。將預收款抵扣課程只是**內部結清**，絕對不能再次增加「人工已確認收款」總額。

## 四、交易與 RPC 邊界（建議）

### A. 超額付款登錄與確認

V5.3 `v5_report_team_payment` 本身仍應保有「禁止超額」的既有語義；V5.4 應建立**獨立且明確的預收款登錄入口**（例如 `v5_report_team_payment_with_advance`），不得悄悄放寬原有 RPC 限制。

登錄後仍為 `pending`。管理者在確認畫面明確看到：
- 本次人工付款總額
- 指定同學生已確認課程的直接分配額（可為 0）
- 差額欲認列為預收款的金額（必須非負）
- 尚未核對銀行交易的警示

管理者確認時，在**同一資料庫交易**內鎖定 Team anchor、付款列及受影響應收列；驗證授權、Team／學生關係、金額守恆、付款 reference 唯一性、可用應收額及未曾確認，接著新增直接分配、預收憑證、稽核並確認付款。任一失敗整筆回滾，保持 `pending`。

若既有 PR #55 的表格限制需要新增欄位或狀態，須採向前 Migration 與明確資料契約，不破壞 V5.3 已確認付款紀錄。

### B. 預收款抵扣建議

提供管理者唯讀 RPC，從**同 Team 同學生**的預收可用額與跨月份未結清應收產生可編輯建議。預設可按課程時間排序，列出科目、授課日期、課程應收、已結清與建議抵扣額。

建議不得寫入資料庫，也不代表已扣款；管理者可調整為部分抵扣，不能選其他學生或 Team 的課程。

### C. 管理者確認抵扣

獨立 RPC 接受預收款 ID 與各課程的分配清單。每次**重新查詢現任 `v5_team_governance.manager_user_id`** 及有效 Team 方案；依固定順序鎖定 Team anchor、預收款、課程應收，檢查：
- 金額大於 0、沒有重複課程、同學生、同 Team。
- 總抵扣不超過該學生預收餘額。
- 每堂課的「直接付款 + 已抵扣」不超過確認應收。
- 同一操作的 idempotency key 唯一，重試不得重複抵扣。
- 交易失敗時無任何部分分錄留存。

確認後新增不可變抵扣分錄和稽核事件。管理者轉讓後，原管理者使用仍有效的舊 JWT 也必須立即拒絕。

## 五、UI 與資料可見性

老師模式 → 設定 → **Team 應收費用（管理者）**，新增：
1. 「人工付款與超額預收」：學生、付款日期、來源、金額、直接分配明細、預收差額、二次確認。
2. 「預收款餘額」：依學生顯示可用預收款，且明確區別「已確認收款」與「預收款已抵扣」。
3. 「建議抵扣」：列出跨科目課程建議，需管理者按「確認抵扣」才入帳。
4. 「操作歷史」：保留付款、預收建立、抵扣、執行者、時間及 references；不能無痕修改。

一般 Team 老師、家長與學生不應經由畫面、RPC、PostgREST 或登出快取讀取到任何時薪、費用、預收款或總額。角色切換／登出需清除客戶端金額狀態。

## 六、隔離驗收必測

- 直接分配 1,000 元 + 預收 500 元 = 人工付款 1,500 元；確認後預收 500 元，不虛增 500 元收款。
- 學生跨科目數學 300 元 + 英文 200 元的建議抵扣，管理者確認前不寫入，確認後餘額 0。
- 多次部分抵扣、不足額抵扣、跨月份抵扣、未來課程無應收不能抵扣。
- 重複付款 reference、重複確認與相同 idempotency key 重送，均不得重複入帳。
- 並發兩次抵扣不得耗盡後產生負餘額；並發付款與預收抵扣不得超過同堂課應收。
- 跨 Team、跨學生、非現任管理者、一般老師、前管理者、家長與陌生 JWT 均拒絕越權。
- V5.3 已確認付款與原稽核欄位不改寫、V4 課程及付款歷史零變更。
- Chromium 真實登入、登錄／確認／抵扣／切換角色／登出，搭配隔離 GoTrue JWT 與 PostgREST、SQL 安全契約。
- 新 Migration 可從乾淨隔離資料庫完整回放，且至少有回滾／恢復策略與上線前檢核。
