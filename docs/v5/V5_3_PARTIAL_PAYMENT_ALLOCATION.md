# V5.3｜人工付款與跨科目部分分配（第一階段）

**Draft PR #55（待驗收），base=PR #54。** 與正式 V4 完全分離；隔離 PostgreSQL 與 Chromium E2E 測試通過前不得合併 Main、套用正式 Migration 或部署 Production。

## 產品範圍

現任 Team 管理者可先人工登錄已自行核對的付款，再把付款分配到**同 Team 同學生**已經確認的課程應收費用。可把同一筆付款拆分成多個科目或多堂課；同一堂課可分次結清。

此操作**不是金流串接，也不驗證銀行確實入帳**。付款方式、日期及金額由管理者人工核對並登錄；家長尚不能自行提交付款，亦不發送確認通知。管理者只能確認分配完整且未超過應收的款項；超額預收款歸 V5.4 開發。

## 資料模型

| 資料表 | 功能 | 權限 |
|---|---|---|
| `tutor_private.v5_team_payment_reports` | 人工登錄付款、學生與 Team 歸屬、日期、方式、獨立 reference、待分配或已確認狀態 | RPC、非前端直接讀寫 |
| `tutor_private.v5_team_payment_allocations` | 一筆付款分配到多堂課、每堂分配 cents | RPC 交易式寫入 |
| `tutor_private.v5_team_payment_audit` | 登錄和正式確認操作留痕 | 僅後端追加 |

新表不新增或修改 V4 `payment_batches`、學生、課程、收款歷史。所有數額以整數 TWD cents 保存。

## 安全與金額守恆

- 三個 RPC：`v5_report_team_payment`、`v5_confirm_team_payment_allocation`、`v5_team_payment_overview`，每次依目前 Team 治理與 Active Team plan 驗證管理者；轉讓後舊管理者以既有 JWT 立即撤權。
- 一次付款最多 100 個科目／課程分配項目，單筆金額必須正數、同學生同 Team；相同課程不能重複列在同一筆分配中。
- **`分配總和 = 付款金額`**，且 **`該課程歷次分配總額 ≤ 已確認應收費用`**；每一堂課的應收列依 UUID 鎖定，避免同時兩筆付款造成競態超收。
- 若確認失敗，全筆資料庫交易回滾；不得只完成一個科目。付款保持 `pending`，可由管理者重試正確分配。已確認付款不能再次確認。
- 每個 Team 的付款 reference 唯一，重複提交不得產生第二筆紀錄。
- 帳務只走私有 schema 及目前管理者授權 RPC；一般老師、家長、學生不會取得金額表或可讀帳務的公開 View。
- 本階段不能隱含預收款／超額付款、退款或人工更正；正式帳務更正須先設計追加紀錄和稽核。

## 介面流程

老師角色 → 設定 → Team 應收費用（管理者） →「Team 人工收款與部分付款分配」。先選 Team、月份及學生，登錄新臺幣金額、日期、方式與備註，再在待分配款項中針對不同已確認應收課程輸入欲分配金額，總和須剛好等於付款金額，確認後列入已分配清單。金額依月份列示；超過當月該學生未清償金額的登錄由 UI 拒絕。

**注意：** 日期／月份篩選為管理者檢視與操作便利；後端金額守恆計算會跨月份累計歷次分配，因此切換月份不會重設付款或清償進度。介面只提供選定月份的課程分配，跨月份手動對帳仍屬後續精修。

## CI 驗收

應確認：合成 Team 多老師、兩科目、同一堂課分次付款、不同科目的單筆分配、重複 reference、超額與未完整分配拒絕、重複確認拒絕、同時兩筆付款不能超收、跨學生與跨 Team 拒絕、一般老師與陌生帳號不可查帳／確認、Team 管理權轉讓後撤權、GUI 登錄／分配／登出 DOM 隱私、V4 正式收款零變更。正式部署與 Production Migration 仍需另行審核。
